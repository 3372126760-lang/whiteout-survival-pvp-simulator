# 正式战斗调用预算优化

更新：2026-10-07。

## 范围

本轮优化集结单波、单撞和333的正式候选筛选。三队列坐标搜索、多波路径搜索及现有Worker并行配置保持原策略。BattleEngine、DamageEngine、HP、回合流程、英雄/兵种技能规则不修改。

旧单波流程仍可通过 `adaptiveSearch: { enabled: false }` 运行；单撞/333也保留旧流程作回归对照。旧benchmark脚本明确使用旧M4=200预算。新默认M4上限150；自定义预算按实际累计上限截取检查点，不伪造阶段。

## 1. 累计样本与配置缓存

原集结流程每阶段独立使用offset：M1=0、M2=100000、M3=200000、M4=300000、Final=500000。因此晋级候选会额外跑各阶段完整预算；旧整阶段evaluation cache只复用相同offset/场次/候选。

新 `BattleSampleLedger` 位于协调器，按完整配置规范化字符串 + seed 保存正式 `FastBattleResult`。每次检查累计预算时只提交缺失seed，既跨阶段复用，也合并同批次及不同来源标签的相同配置。不跨搜索session持久化缓存。模板缓存与结果缓存分开计数。

规范化保留全部 `ValidationBattleInput` 字段，递归排序对象键、保留数组次序，只把单独传入每场的randomSeed/simulationMode统一。A/B英雄、车身runtime/等级、专武、兵种数量/等级/混兵、T12、历史/当前属性与加成、场景、战后模式、服务器阶段、禁用技能和触发覆盖均参与。使用完整字符串作相等键，避免短hash碰撞误命中。对不影响引擎的输入元数据也保守保留，可能造成额外miss，不会越过字段差异误复用。

候选来源 `selectionReasons` 不属于正式战斗输入，所以5%/2%/1%/回流的相同配置可以复用。候选配置在一次搜索内固定；更改用户配置会开启新session。

### Seed规则

筛选共用同一递增prefix。Final保留已用筛选prefix，剩余使用offset=500000起的新验证seed；生成时排除与筛选seed碰撞及重复值。默认150筛选+850独立验证=1000。即使自定义Final很小，也至少保留一半独立seed。场景根seed相同，RNG仍由原引擎生成。

例如5→30→50→150→1000：只执行5+25+20+100+850=1000。同一配置/seed不重复执行。如果中间预算比Final更大，部分筛选样本不会用于Final；独立验证仍保留，最终n与全部历史执行量分别报告。

## 2. M4 / Final Racing

- M4默认累计50→100→150；Final默认累计300→500→1000。若精搜回流候选已有更多共同样本，跳过更低检查点，不倒退到少量样本重新筛选。
- 使用Wilson区间，按本阶段候选数×检查次数收紧置信水平，默认familyErrorRate=0.01。Wilson是近似统计区间；收紧区间用于降低多次筛选风险，不宣称严格全局最优或绝对不误杀。
- 淘汰条件：`upper_i < kthLower - tolerance`；默认tolerance=0.005。kthLower取全部候选的第K高下界。
- Top-K点估计候选和明确保护的当前/已知强方案不做CI淘汰。普通最低30场；uncertainty≥0.35最低100场（受当前最大预算限制）。改变车身时丢弃旧车头方案的Theory估算，按未知/高不确定性保护。
- M1覆盖所有合法车头后才允许后续预算分配。M2/M3保留原Top-K晋级规则；M4完成最大预算后仍按正式结果晋级，不用TheoryScore决定Final排名。
- 所有未被置信淘汰的Final候选继续到最大预算；Top1至少达到minimumFinalRuns（默认1000，受用户Final预算限制），重叠的Top1/2/3继续验证。被明显支配的非保护候选可以停在300或500。
- 当前方案使用原始精确input，始终进入Final并与推荐一起排序。若当前英雄不满足优化器近三代规则，作为受保护baseline参与Final，不当作M1生成的合法车头。
- 记录wins、losses、n、上下界、检查点和confidenceDominated/protectedByUncertainty/protectedByTopK/protectedReference/notTopK/maxBudgetReached原因。平局/超时在胜率分母中保留，不作为胜利。

## 3. 多basin的5%→2%→1%

多个basin按已有每车头数量/距离保护选出，各自维护center、历史centers、bestRatio、扩张轮数、生成数量及stopReason。

每个中心只探查六个合法的零和邻居，加中心共最多七点；共同seed保证成对比较。5%使用已有边界预算、2%只做局部邻居，并用正式成对胜负分歧的Wilson证据判断方向。在逐seed胜负完全相同时，只有逐seed剩余兵数Pareto支配才作为次目标提升证据，不制造胜率梯度。

2%存在统计提升的basin才进入1%邻居步进，默认最多三轮。连续两次没有置信提升则停止；相同闭合邻域第二次可全部命中缓存，不额外跑引擎。`flat2Percent`表示本轮限定预算没有观测到置信提升，不等于证明该区域数学上完全平坦。多个basin互不阻止；不退化成只搜索全局Top1。

非整数比例的单撞baseline只参与精确配置比较，不作为整数优化网格的中心。2%/1%候选走原有整数比例和属性固定转换；不搜索装备或属性。

## 4. 报告与UI

SearchIntegrityReport增加每阶段进入/淘汰/晋级、requestedBattles/executedBattles/reusedBattles/cacheHitRate/elapsedMs，以及Racing检查点、保护计数、淘汰原因、2%/1%basin与生成比例数、Final各检查点及筛选/独立验证执行量。

性能表及报告总计显示请求、执行、复用和复用率。`cacheHitCount`为正式结果复用数，`templateCacheHitCount`单列静态缓存。新累计阶段满足requested=executed+reused；CI淘汰后的未申请后续预算不计为requested。请求数包含每次累计检查所需的已有样本，因此增加检查点可能提高requested，而executed才是实际引擎调用量。cacheHitRate=reused/requested，不是省掉的旧流程预算比例。

`final.screeningRuns`统计本次搜索所有阶段实际执行的筛选seed；`final.independentValidationRuns`统计实际执行的独立验证seed。两者合计等于本次搜索实际调用量，不能把screeningRuns理解为只有Final使用的150场prefix。候选最终trials只统计参与该次排名的样本，不一定等于该候选全部历史执行量。

计时开启时Integrity含阶段elapsed；关闭时elapsed为0，以保持排除计时字段后的确定性。计时不参与seed、晋级或排名。原有节流进度/ETA/复制性能JSON保留；高级调试可查看完整搜索完整性报告。

## 6. 完整实测

下方对照来自同一批顺序运行的正式BattleEngine，未使用模拟返回值替代实测。两组输入均为现有六英雄、等面板的合成测试场景，根seed=91；不是游戏战报拟合，也不能证明其他场景的全局最优。旧流程M4为200场，新流程M4上限150场；两者Final上限1000场。独立2000场冠军验证在搜索计时与调用预算之外单列。
