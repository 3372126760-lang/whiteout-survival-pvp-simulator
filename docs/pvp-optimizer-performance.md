## FastBattleMode

入口：`src/pvp/battle/fastBattleMode.ts`。

```ts
FastBattleMode.run(template, { maxRounds, troopSkillSystem, heroSkillSystem })
// { outcome: "A" | "B" | "draw" | "timeout", roundCount, remaining: { A, B } }
```

`resolveRoundFast` 调用原有 `resolveRoundInternal`，仍按原顺序执行行动、技能、伤害、伤亡及状态推进。关闭 BattleLog、BattleTrace、技能详细日志及伤害报告汇总，不返回整份 BattleState。单场调试、普通批量模拟的现有日志模式保留。

引擎内部仍创建结算及技能链需要的临时 DamageEvent，其中包含原 DamageEngine 必须提供的字段；本轮没有删改这些字段或另写一套伤害计算。快速模式省掉的是可省略的日志、报告和归因汇总，临时事件在本回合结束后释放。

三队列通过 `runThreeQueueScenarioFast` 使用同一个队列调度函数，省掉逐场战报、队列过程日志和战后展示统计；返回胜方、实际回合数及剩余兵数。未分出胜负的队列战仍按原规则记作失败样本。

## 静态模板与隔离

| 层次 | 缓存内容 | 更新方式 |
|---|---|---|
| 静态技能 | 技能定义、效果、解析后的技能系统、启用集合及触发覆盖 | 搜索会话/Worker 内复用；禁用技能或覆盖配置变化时独立建立 |
| 候选战斗 | 英雄阵型、已修正属性、等级/HP、初始技能状态 | 候选跨阶段复用；属性、英雄、等级及其他战斗配置参与缓存键 |
| 三队列配对 | 每个候选最多九种队伍配对模板 | 首次遇到配对时建立，后续只替换兵数 |
| 每场动态状态 | 兵数、残血、技能计数、临时护盾及状态容器 | 从初始模板复制；每场重置 RNG |

`createValidationBattleCompiler` 将技能解析缓存与具体候选人数分开，使同一搜索内不同英雄/比例候选也能复用静态定义。候选模板使用有上限的 LRU：普通候选 128、三队列候选 32、多波输入 16；静态技能配置最多 32 种。缓存随搜索 Worker 结束释放。

多波下一战仅继承敌军整数兵数，英雄技能状态、回合、HP 和护盾从初始模板重新开始。人数相关的兵种状态仍调用原 `createTroopState`，没有复制或更改 HP 公式。混编转下一波的原有等级处理保持一致。

## 提前淘汰

入口：`src/pvp/optimizer/earlyElimination.ts`。

至少运行 20 场，每增加 10 场检查一次。以同阶段**已完整评估**的最佳候选作参照。使用单侧 Hoeffding 界：

```text
alpha = 0.01 / (2 × 候选比较数 × 最大检查次数)
radius(n) = sqrt(log(1/alpha) / (2n))
upper = min(1, wins/n + radius(n))
lower = max(0, wins/n - radius(n))
```

仅在候选 `upper < 最佳候选 lower` 时停止。误差预算按候选和重复检查分摊。种子仍是该阶段共同种子的前缀；实际执行数、节省数和淘汰数单独记录。

部分样本不进入下一阶段或最终排序。最终候选和原始当前配置始终执行完整的验证预算。淘汰是搜索近似，不能保证全局最优；胜率接近时不会强行提前停止。

`minRallies` 及多波搜索的目标还包括敌军消耗，不能用单波胜率提前淘汰这类候选，因而该路径保持完整轨迹采样。

## Worker 并行

- `optimizerWorker.ts` 作为协调器，`optimizerCandidateWorker.ts` 计算候选。
- 最多使用四个子 Worker，并预留一个逻辑核心。不可构造 Worker 时使用同一快速执行器顺序计算。
- 单撞、333、三队列及多波序列均支持候选并行；同一三队列坐标下降的下一步仍等待本步结果。
- 同一个候选尽量路由到同一 Worker，复用模板。多波序列也参与路由键，避免所有序列落到单一 Worker。
- 粗/复筛按固定四个候选一批更新统计参照；结果按提交顺序归并，与 Worker 完成先后及核心数无关。
- 每个 Worker 独立缓存与 RNG。计算错误正常返回到 UI，完成/失败时释放池内 Worker。
- 结果页展示实际随机样本数、淘汰数、节省数、模板命中和 Worker 数。多波的一个随机样本表示一条完整轨迹。

## 验证与复现

```powershell
npm.cmd run typecheck
npm.cmd run lint
npm.cmd test
npm.cmd run build
npm.cmd run verify:optimizer-workers
npm.cmd run benchmark:optimizer
```

`optimizerPerformance.test.ts` 覆盖固定种子的全日志/快速模式对照、S8/S11、T12/混编、三队列调度、下一波重建、模板隔离、淘汰与完整复验、同步/异步排名，以及 Worker 提交顺序与释放。

`verify:optimizer-workers` 在四个真实 Node 线程中运行 **Vite 构建后的候选 Worker 包**，只适配消息接口，核对单战、三队列及多波结果与顺序执行一致。这验证实际并行及构建包执行；浏览器的 Worker 加载仍需可用浏览器实测。本环境浏览器工具没有可用浏览器。

`benchmark:optimizer` 比较既有 compact 模式、快速模式、跨候选技能缓存及三队列完整日志/快速模板路径，并输出相同样本数的实际回合数。短回合、无英雄基准不能代表全部实战阵容，实测记录见 `examples/optimizer-performance.txt`。

既有重复车身英雄的入场唯一性失败属于单独的规则问题，本轮没有调整该检查。

### 本次验收（2026-09-28）

- 类型检查、Lint、引擎及 UI 生产构建通过。
- 全套 `npm.cmd test`：647 项中 646 项通过；唯一失败为既有重复车身英雄入场唯一性检查。新增性能测试 11 项通过。
- 构建后的 Worker 包在四个真实线程运行 20 个任务，单战、三队列、多波的固定种子结果与顺序执行一致。
- 本地限定基准：三队列 30 个相同种子、2692 个相同回合，完整日志 1367.8 ms、快速模板 458.9 ms，约 2.98 倍速度。
- 明显落后候选执行 20/200 个样本后淘汰，节省 180；未据此缩短最终候选或当前方案复验。
